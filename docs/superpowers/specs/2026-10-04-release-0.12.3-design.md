## 2. What is left

**F1 (P1, security). Commands are still printed by interpolation, one of them injectable.**
`renderSendPreparation` (`packages/gmail/src/cli/render.ts:663`) prints `agent-gmail send execute … --expect-subject
<subject>` with the subject in `JSON.stringify` quotes. JSON quotes are not shell quotes: inside double quotes a POSIX
shell and PowerShell run `$(…)` and backticks, and cmd.exe expands `%NAME%` before it reads quotes at all. The subject
comes from the draft, and a reply's subject comes from the email being answered, so its sender chooses it; pasting
the printed line could run their command. The same line also leaves out `--expect-cc` and `--expect-bcc`, which
`send execute` checks (`packages/gmail/src/cli/program.ts:1218-1225`), so for a draft with Cc or Bcc the printed
command fails its own expectation check. And `024b827` left about thirty other printed commands built by template
literals — in the Gmail, Slack and WhatsApp renderers, and in operation results, hints and MCP text across all four
channels (Codex review, round 1, finding 2, lists each with path and line). Most carry only generated or validated
values and run as printed on POSIX, but on Windows none of them goes through the rule CUE-306 and CUE-398 set, so the
claim that "every printed command runs as shown on Windows" is not yet true. The operation contexts of Gmail, Slack
and Resend cannot be told which platform to print for; only WhatsApp's can.

**F2 (P2). Between the claim and the provider, a failure can leave a slot taken, an approval `sending`, and the
first error hidden.** Gmail's certain refusal (`packages/gmail/src/operations/send.ts:573`) releases, completes the
approval, then audits, as one chain; Resend's (`packages/resend/src/operations/send.ts:536`) completes before it
releases. A step that throws skips the rest and replaces the provider's refusal. The same is true earlier: Gmail can
fail reading the draft after reserving capacity, or when releasing on a changed draft (`send.ts:549-558`); Resend can
fail writing its attempt record or its durable `started` audit before the provider is called (`send.ts:488-501`).
Those are certain no-sends, yet they keep the slot and leave the approval `sending`, which later reads *unknown*. On
the unknown-outcome path, a failure writing the audit or the local record can likewise replace the *unknown* error.

**F3 (P2). `reactions.remove` answering `no_reaction` is recorded as failed.** Slack documents `no_reaction` as "the
specified reaction does not exist, or the requestor is not the original reaction author"
(docs.slack.dev/reference/methods/reactions.remove). Either way, this account has no such reaction on the item, which
is what the removal asked for. It does **not** prove the emoji is absent: another member's reaction may remain.

**F4. The Slack CLI test of a printed widening command fails on Windows.** The test (`packages/slack/test/
cli.test.ts:1610`) expects `--port 60426`; on Windows `shellCommand` prints `--port "60426"`, as designed (a word that
starts with a digit may be read as a number by PowerShell, `cli-runtime.ts`). The product is right; the test's CLI
helper inherits the host's platform.

**F5. The Gmail CLI quoting test fails on Windows.** Its POSIX case (`packages/gmail/test/cli-quote.test.ts:57`)
expects the client file's path with `/`; the path is built with `join`, so on Windows it has `\`.

**F6. Release readiness.** The root version is 0.12.2 and `CHANGELOG.md` has no 0.12.3 section. The notes drafted on
2026-10-03 said printed commands do not change on macOS and Linux, which is false (WhatsApp's handoff hints gained the
`--source`, chat and account arguments they had been missing), and did not list the additive interface changes.

## 3. Decisions

**D1. Every command printed to be run is built as words, by one rule, for a platform that can be injected.**

- Each channel package's operation context gains an optional `platform` (default `process.platform`), as WhatsApp's
  already has; each CLI already takes one. Every command a renderer, an operation's result or hint, or an MCP text
  prints for a person or agent to run is built as `shellCommand(words, platform)` and shown through
  `inlineCommand`/`commandText` (or carried as a `ShellCommand` until it is shown). This covers every site the round-1
  review listed and any found while converting; values that are generated or validated go through it too, so there is
  one rule to audit rather than a judgement per site.
- The Gmail send command prints, as words: `agent-gmail send execute <draft> --inbox <inbox> --approval <id>
  --expect-to <to…|none> --expect-cc <cc…|none> --expect-bcc <bcc…|none> --expect-subject <subject|none>`, each list
  as separate words after its flag, as the variadic options parse them.
- **`none` for the subject.** Today the CLI turns `--expect-subject none` into `''` (`program.ts:1229`), so a draft
  whose subject is literally `none` can never pass the check from the CLI. From 0.12.3 the CLI no longer flattens it:
  it passes `executeSend` an explicit marker that the subject expectation was the CLI's `none`. `executeSend`, which
  reads the live draft before it claims (`send.ts:522-525`), then accepts exactly two candidates — the live
  subject, trimmed as core trims it, is `''` or `'none'` — and passes that live subject as the expectation to
  `claimForSend`; for any other live subject it passes `'none'`, which cannot match, so the refusal (and the voiding
  that an `expect` mismatch causes) happens in `claimForSend` exactly as today. A whitespace-only subject counts as
  empty, as core's trimmed comparison already treats it. Core's comparison (`sameExpectation`, `approvals.ts:1097`) is unchanged, and so is MCP, whose subject is an
  ordinary string. This keeps every existing use working and closes the gap without loosening the check for any other
  subject; the approval still binds the draft's exact content.
- **Structure first, a lint as backstop.** A result field or hint that carries a command to run carries a
  `ShellCommand` (or text made from one by `inlineCommand`/`commandText`) — never a string assembled from parts. A
  root-suite test scans `packages/*/src/**/*.ts` for a template literal or concatenation that begins a printed command
  (`agent-gmail `, `agent-slack `, `agent-resend `, `agent-whatsapp `, `agentcomms `, `npx `) and fails naming file
  and line, with a commented allowlist for prose. It is labelled in its own comment as a **best-effort lint**: it
  catches the direct spelling that caused F1, not every indirect construction (a word list joined with spaces evades
  it), and it carries fixtures proving it fails on a direct template and passes on a `shellCommand` call. Review
  remains the guard for indirect construction.
- `SendPreparation.nextStep` carries only a generated approval id or prose (`send.ts:395`) and is not injectable; it
  is converted under the one rule all the same.

**D2. After the claim, until the provider is asked, every failure is a certain no-send, and its bookkeeping runs as
independent steps.**

- The *certain no-send region* is everything after capacity is reserved and before the **outbound send request**
  is issued, plus a refusal the provider certainly gave (the existing allowlists). Gmail: the post-reservation draft
  read and the changed-draft check (`send.ts:549-569`) — Gmail may have been asked to *read*, never to send. Resend:
  writing the attempt record and the durable `started` audit (`send.ts:489-501`); its draft reload happens before the
  claim (`send.ts:458`) and is outside the region. Any failure in the region runs the same bookkeeping, each step
  attempted on its own whatever the others did, in this order: release the capacity slot; complete the approval as
  `failed`; write the local record where the channel keeps one (Resend); append the audit.
- **A cap refusal keeps today's behaviour.** Capacity is reserved after the approval is claimed (`approvals.ts:766`,
  then Gmail `send.ts:549`, Resend `send.ts:488`), so a cap refusal (`RATE_CAPPED`) takes no slot (the ledger refuses
  before it appends, `ledger.ts:92`, `store.ts:144`) and completes the claimed approval as `failed`: nothing was sent,
  and the send is prepared again once capacity frees. That is what both channels have always done. The base design's
  step 1 lists `RATE_CAPPED` among refusals that "leave the record untouched", which the code has never done, because
  the cap is checked in its step 2, after the claim; that sentence is corrected to match the code. Reserving before
  claiming, so a capped approval could be reused, was considered and left out: it reorders the single-use claim in a
  patch release, for an inconvenience nobody has reported.
- **A reservation whose write throws** may have committed: the append can land before the close or sync fails
  (`packages/core/src/fs.ts:105-121`; Resend appends inside `reserve`, `store.ts:153`). So release is attempted
  independently — for capacity accounting, releasing a reservation that was never recorded is already a no-op
  (`ledger.ts:65`, `store.ts:138`), though its own tombstone append can throw and is then reported — and the approval
  is completed `failed` as today; a failure of either is added to the hint without replacing the reservation's own
  error.
- **The caller sees the first error**, not a bookkeeping one: the error thrown keeps the original's `code`, `message`
  and `details`, its hint is the original hint followed by each bookkeeping failure, and its `cause` is the original
  error object itself. When the original is not a `CommsError`, it is wrapped as today and the same rule applies to the
  wrapper.
- **On the unknown-outcome path** nothing is released or completed (the slot and the `sending` approval are how an
  unknown outcome stays visible); the audit and local record are attempted independently, and their failures are added
  to the *unknown* error's hint without replacing it.
- Slack's `recordReactionRefused`/`refusalWithBookkeeping` (`packages/slack/src/operations/send.ts:1278-1285`) are the
  precedent for "attempt independently, keep the provider's answer visible"; Slack has no capacity slot or local
  record, so the order above is this design's, not copied from it.

**D3. `no_reaction` on a removal counts as done, worded for what it proves.** It leaves `reactions.remove`'s refusal
allowlist (`packages/slack/src/api/call.ts:312`), and the removal is recorded through `recordReactionChanged` as used,
with the note: "Slack says this account had no such reaction on the message, so there was nothing of yours to remove;
reactions other people added are not affected." The CLI's and MCP's description of the removal says it removes *your*
reaction. On `reactions.add`, nothing changes.

**D4. Tests that check printed text pin the platform.** Every test asserting a printed command — CLI, operation
result, hint or MCP text — passes the platform explicitly (`darwin` for the POSIX text) through the CLI's option or
the new context option, instead of inheriting the host's; Windows rendering is asserted by tests that pass `win32`. A
path in an expected string is built from the real path, never written with one separator. The production default stays
`process.platform`. The list is closed by a search, not by memory: before converting, the builder runs
`git grep -nE "agent-(gmail|slack|resend|whatsapp) |agentcomms |npx " -- ':(glob)packages/*/test/**' 'test/**'`
(87 files at `1b1fe3e`) and records in
the implementation report every assertion on printed command text it finds, each marked pinned, made
platform-aware, or not a printed command (with why). The reviews so far name at least: Gmail `registration.test.ts:590,
638, 760`; Slack `cli.test.ts:476, 550, 1278`, `cli-files.test.ts:375`, `app.test.ts:211, 251, 502`,
`mcp.test.ts:297`, `mcp-changes.test.ts:296, 333`; Resend `mcp.test.ts:164`; WhatsApp `cli.test.ts:33`,
`chat-lists.test.ts:151`.

**D5. It ships as 0.12.3, a patch.** Nothing is removed and no input is narrowed. The release notes lead with the
security fix and list what changes in what the tools return: an optional `note` on Gmail and Resend send results and
on Slack reaction results; `already_reacted` and `no_reaction` now succeeding (exit 0) instead of failing;
`--expect-subject none` also matching a subject of `none`; core's exported `DownloadAtTerminalOptions.command`
widened to `string | ShellCommand`; WhatsApp's handoff hints carrying their missing arguments; and printed commands on
Windows quoted by the common rule (a number word such as a port in double quotes). It is released through the
tag-triggered CI after a green six-platform dry run of the exact commit to be tagged.

## 4. Tests owed

Each guard is watched failing under a mutation, then restored.

- **D1, Gmail send command:** the printed line, for darwin, parsed back through the Gmail CLI's own option parser
  gives exactly the draft id, inbox, approval and the To, Cc, Bcc and subject expectations — for several and for no
  recipients in each list, an empty subject, a subject of `none`, a subject starting with `-`, and subjects holding
  `$(whoami)`, a backtick, `%PATH%`, a double quote, a single quote and a line break; for win32, each of those subjects
  either prints a line that parses back the same or (for `$`, the backtick, `%`, `"` and the line break) prints no line
  and the JSON form; a single quote alone prints a line. `send execute` with `--expect-subject none` passes for an empty
  subject, a whitespace-only one and `none`, and refuses (voiding the approval, as an `expect` mismatch does today)
  any other subject.
- **D1, everywhere else:** each converted site, on darwin and win32, through the surface that shows it (CLI text, JSON
  result, MCP text); the guard test fails when a raw `agent-… ${…}` command string is added to a source file.
- **D2, Gmail:** a failure injected into the post-reservation draft read, the changed-draft check, and a certain
  refusal; and, for each of those, into each bookkeeping step (release, approval completion, audit), one at a time and
  two at once. A cap refusal takes no slot, completes the approval `failed` and reaches the caller as
  `RATE_CAPPED`; a reservation write that throws attempts release and completes the approval `failed`. The pre-claim draft read is untouched.
- **D2, Resend:** a failure injected into the attempt record, the durable `started` audit, and a certain refusal;
  and, for each, into each bookkeeping step (release, approval completion, local record, audit), one at a time and two
  at once. A cap refusal and a throwing reservation write as for Gmail.
- **D2, both:** every bookkeeping step is attempted in every case; a release failure is reported in the hint;
  capacity is released whenever the release step itself succeeds; the caller's error has the original `code`,
  `message`, `details`, hint prefix, and as `cause` the very object first thrown — a non-`CommsError` included. A
  certain refusal releases the slot; an unknown outcome keeps it and the approval `sending`, and an injected audit or
  record failure there leaves the error *unknown*.
- **D3:** `reactions.remove` answered `no_reaction` succeeds with the note, through the CLI's JSON and through MCP,
  with an injected approval or audit failure still succeeding with that failure in the note; `reactions.add` answered
  `no_reaction` is unchanged; the allowlist test no longer lists `no_reaction` for removal.
- **D4:** F4's and F5's tests pass on any host and fail when the behaviour they guard is broken.
- The repository's full `pnpm verify`, then the six-platform dry run, both green on the commit that is tagged.
