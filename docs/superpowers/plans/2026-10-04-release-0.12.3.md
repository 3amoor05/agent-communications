# 0.12.3 — implementation plan

Spec: [2026-10-04-release-0.12.3-design.md](../specs/2026-10-04-release-0.12.3-design.md). Base: `release/0.12.3`
(`1b1fe3e`). Two tracks touch mostly different code and are built in parallel worktrees, then combined on
`release/0.12.3`. Every task writes its tests first and watches them fail; every guard is mutation-tested (break it,
see a test fail, restore it) and the mutation recorded.

## Track A — printed commands (D1, D4) · branch `fix/0123-printing`

1. **The two Windows tests (F4, F5).** Slack's CLI test helper (`packages/slack/test/cli.test.ts`) takes a
   `platform` and passes it to `run`; the widening test pins `darwin`. Gmail's `cli-quote.test.ts` builds its expected
   path from the real path (escaped for the regex), not `/`-separated text.
2. **Platform in the contexts.** Gmail, Slack and Resend operation contexts gain `platform?: NodeJS.Platform`
   (default `process.platform`), as WhatsApp's has; the CLIs and MCP servers pass theirs through.
3. **Convert every printed command.** Each site from the round-1 review's finding 2 and any found on the way:
   build words, `shellCommand(words, platform)`, show with `inlineCommand`/`commandText`. Gmail's send command prints
   `--expect-cc` and `--expect-bcc` and each list as separate words.
4. **`--expect-subject none`** is satisfied by an empty subject or the subject `none`, wherever the expectation is
   checked; any other subject is still compared exactly.
5. **Guard test** in the root suite (`test/`): scans `packages/*/src/**/*.ts` for a template literal or concatenation
   that starts a printed command (`agent-gmail `, `agent-slack `, `agent-resend `, `agent-whatsapp `, `agentcomms `,
   `npx `) and fails, naming file and line, unless the line is on its commented allowlist of prose mentions.
6. **Pin the platform in tests** that assert printed text (D4's list and any the conversion touches); add win32
   cases for each converted surface.
7. Regenerate what is generated (`pnpm sync:reference`, `pnpm sync:skills`) if any description changed.

## Track B — send bookkeeping and reactions (D2, D3) · branch `fix/0123-bookkeeping`

1. **A no-send bookkeeping helper per channel** (Gmail, Resend), or one shared shape if it falls out naturally:
   attempts release → approval `failed` → local record (Resend) → audit, each independently, collecting failures;
   returns them for the hint.
2. **Route the certain no-send region through it:** Gmail's draft read and changed-draft release after
   reservation, reservation failure, and the certain-refusal allowlist; Resend's attempt record, durable `started`
   audit, reservation failure, and certain refusal.
3. **Error shape:** throw an error with the original `code`, `message` and `details`, hint = original hint + each
   bookkeeping failure, `cause` = the original error object.
4. **Unknown-outcome path:** audit and local record attempted independently; failures appended to the *unknown*
   error's hint; slot and approval untouched.
5. **`no_reaction` on removal:** out of the `reactions.remove` refusal allowlist; recorded through
   `recordReactionChanged` with D3's note; CLI and MCP removal descriptions say "your reaction".
6. Tests: the D2 and D3 matrices from the spec's §4.

## Combining and shipping (done by the reviewer, not the builders)

1. Review each track's diff, run its package suites, repeat a sample of its mutations; commit on its branch.
2. Codex code review of each track against the spec; fix until READY-TO-MERGE.
3. Cherry-pick both onto `release/0.12.3`; resolve any overlap in the three `send.ts` files.
4. Version 0.12.3 (`pnpm sync:versions`), the 0.12.3 `CHANGELOG.md` section per D5, full `pnpm verify`.
5. Push; six-platform dry run (`gh workflow run release.yml --ref release/0.12.3 -f dry-run=true`) green.
6. Merge to `main`, tag `v0.12.3`, push the tag; watch the release run; check the six packages from npm in a throwaway
   home; close CUE-395–398 in Linear with the release link.
